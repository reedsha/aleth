# MASTER CONTEXT — Ground Truth Architecture Manifest

## 1. System Identity & Core Rules

**Identity.** Aleth Studio — a local, single-machine AI IDE. A **micro-kernel** with a SQLite state kernel, a stateless Swarm worker dispatcher, and deterministic tier routing. The LLM plans; the engine executes what a human approved. No daemon, no server, no cloud state.

**Absolute constraints (violating one is a failed batch):**

1. **Zero native terminal fallbacks.** Execution is contained, not merely filtered. Every command the app did not author goes through `tools/docker_sandbox.py`: `tools/mcp_exec_server.py` (the model's shell) and `tools/test_runner.py` (pytest, which imports and executes workspace code). A container is launched with `--network=none`, `--user <uid>:<gid>`, the workspace as the only OCI bind mount and the container's cwd, CPU/memory/pids capped at a **bounded** default (512 MB, one CPU, 64 pids) that nothing can raise past a hard ceiling, `--cap-drop=ALL`, `no-new-privileges`. When the runtime cannot be reached the run is **refused**, never executed on the host: no host Python process may import or execute code inside the workspace. There is no unsandboxed fallback and no `shell=True` in any production module; the old in-process perimeter (`tools/sandbox.py`) is deleted.
2. **Pydantic schema strictness.** Every JSON boundary is a strict model (`extra="forbid"`). A field that is missing is an error, not a default. Softer-than-required defaults hide bugs.
3. **Process-isolated workers.** A Swarm worker is a plain picklable function crossing a `ProcessPoolExecutor` boundary. No live SQLite connection, no MCP session, no closure crosses it. Workers cannot emit UI events — the **parent's** `Future` callback does.
4. **No N+1 database queries.** Dispatch eligibility and every per-node input are decided in **one** SQL statement. Never a scalar `SELECT` inside a dispatch loop.
5. **SQL decides graph state.** `task_dependencies` is the single source of truth for edges. Eligibility is a `NOT EXISTS` query (`orchestration/scheduler.py::_EXECUTABLE_SQL`), never rebuilt in Python.
6. **One authority per decision.** The router picks the model and its endpoint. The worker applies them verbatim and never guesses. No hardcoded fallback model anywhere on the execution path.
7. **Code reads like the domain.** `max_retries` means *retries* (`rejection_attempts <= ?`). Do not bend a constant to mask an off-by-one in SQL.
8. **No dead fallbacks, no silent degradation.** A missing declaration fails loudly. A capability that cannot be resolved is an error, not an empty tool set.

**Database (`storage/db.py`, SQLite).** `tasks` carries, besides the DAG/projection columns: `complexity_score` (1–5), `rejection_attempts`, `rejection_feedback` (JSON), `system_failures`, `required_capabilities` (JSON). Added by guarded `_MIGRATIONS` (`PRAGMA table_info`), also present in the `CREATE TABLE` text. **`CREATE TABLE IF NOT EXISTS` never adds a column to an existing table** — new columns must go in `_MIGRATIONS`.

**Dependencies.** Locked in `pyproject.toml` (pydantic, openai, numpy, lancedb, pyarrow, torch, transformers, filelock, `deepagents`, laya, langchain-core, langchain-openai, astchunk, python-dotenv, pywebview, PyYAML; `test` extra: pytest, pytest-xdist). `deepagents_core` is the in-repo editable Rust crate (`crates/deepagents_core`, `pip install -e crates/deepagents_core`) — not on PyPI. Two names keep the `deepagents` spelling after the rebrand, and both are load-bearing: the `deepagents` PyPI framework (`from deepagents import create_deep_agent`) and the `deepagents_core` crate.

**Bootloader (`core/config.py`) — Phase 6.5.** Strict `TierConfig`/`BootloaderConfig` (tier_0 may omit `api_key`; tier_1/tier_2 must declare one). `boot_or_exit()` is called by `main.py` **before** anything imports `registry`/`app` (both open the store on import). It probes every configured tier with `GET {base_url}/models` and `sys.exit(1)` on a timeout, 401 or 404. `default_config()` derives the fleet from `agents/model_routing` + `OPENAI_*`, so the router has exactly one source. `aleth.config.example.json` is a valid, copyable example.

**DAG creation — nodes are born armed.** `required_capabilities` is a **birth** field, not something the worker discovers. `merge_dag_fields` enforces a strict **union-or-refuse strategy** on replans to prevent capability starvation.
Verified: the Rust canonicaliser (`deepagents_core.prepare_plan_state`) preserves the key. **Zero starvation pass: tick one is equipped.**

**Router (`orchestration/model_router.py`) — Phase 7 infrastructure.**
`route(complexity, rejections)` is pure and abstract. `resolve_endpoint(routed, config=None, *, refuse=True)` applies the fallback matrix: exact tier, else CRITICAL + strongest configured tier **at or below**; but tier_2 required with only tier_0 configured → `TaskUnroutable`. `Swarm.tick()` catches that and fails the node with the reason instead of dispatching it.

**Agent routing gateway (`orchestration/routing.py`) — Phase 19.** The *agent* decision — System 2's Architect or a System 1 Coder — is a typed, injectable, auditable step, not an implicit consequence of a title. `classify_task(text, tag=, classifier=)` **never raises**: a classifier that fails, times out or answers off-contract routes to the **Architect** with `CLASSIFIER_FAULT` logged at `CRITICAL`, never a silent downgrade to a Coder. High complexity is an administrative intent **or** a `core` domain; everything else is a Coder. The classifier is a parameter, not a global lookup — the default is `agents.laya_model.classify`, and a test injects a fake. `Swarm._descriptor_for` calls it on the **parent** side of the pool boundary (so a plain callable is safe), appends the decision to the `routing_decisions` ledger (`storage/telemetry.py`; its own append-only table and indexes — a routing decision is not a container execution, so it does not overload `execution_telemetry`'s `execution_id`/`exit_code` contract), and ships the decision to the child in the descriptor. A ledger write failure is reported on stderr and dispatch continues. The **model** tier stays `model_router`'s authority — a classifier band is a second, independent input, and collapsing them would put two owners on the model choice.

**The System 1 seam is injectable (`agents/laya_model.py`) — Phase 19.** `install(resolver)`/`installed()` are the dependency-injection seam: `classify` answers from whatever resolver is installed, and reading `LAYA_BACKEND` is only how the *default* resolver is built. This closes a real latent flake: `env_boot.load_environment()` loads `.env` with `override=True`, so a test that imported `app` mid-process re-armed `LAYA_BACKEND=model` for every later test in that worker — the characterization suite's answer then depended on ordering, not on the test. `tests/conftest.py` now injects a deterministic word-list resolver per test (`autouse`), so the ambient environment is irrelevant; the one test that needs the live checkpoint is `tests/test_laya_live.py`, marked `llm`, and CI runs `-m "not llm"`.

**Transport — the tier's endpoint is used.** `resolve_endpoint` routes to `execute_node` → `plan_task(base_url=, api_key=)` → `_from_llm` → `system2.complete` / `complete_with_tools`, which build the client from the **tier's** endpoint. A keyless local tier gets `LOCAL_ENDPOINT_KEY`.

**Swarm (`orchestration/swarm.py`) — reactive, no generator, no polling.**
`tick()` dispatches runnable nodes and `Future.add_done_callback` delivers completions on the parent thread. Rejection state lives in SQLite, never in the Swarm object. Failure segregation: `is_system_failure()` → counted in `system_failures`, node stays `pending` and is auto-retried up to `max_system_retries` (3). UI event emission is strictly isolated to the orchestration layer.

**Context diet (`orchestration/mcp_session.py`) — Phase 7.4.**
`MCPSessionContext(root, capabilities=…)` scopes servers spawned **and** tools bound. `fs`→read_file/create_file, `exec`→execute_command/execute_restricted_command, `ast`→list_symbols/edit_ast_node/append_to_file. `[]` → **no servers, no tools**. 

**Semantic lock (`tools/semantic_index.py`) — Phase 8.1 (done early).**
`MiniLmEmbedder._ensure_loaded` takes a per-model `filelock.FileLock` around the weights load, avoiding race conditions in the Hugging Face cache.

**The image is the Python toolchain, and the runtime is chosen per project — Phase 30.** `docker/sandbox.Dockerfile` is `python:3.12-slim` plus pytest and its neighbours, and it carries **no other language**: node was added in Phase 29 and removed in Phase 30, because a runtime the project does not use is weight every project pays for and a monolith grows into a CVE surface nobody audits. `tools.project_phases.detect_runtime` reads the project's own manifests (`package.json` → `node`, `requirements.txt`/`pyproject.toml`/`setup.py`/`pytest.ini`/`tox.ini` → `python`) and `detect_image` maps that to the image a phase runs in — `aleth-sandbox:latest` (the Python toolchain) or `node:20-alpine` (stock, and enough for `npm install`/`npm test` because the project's own dependencies come from the setup phase). A **polyglot** project is refused rather than guessed, and declares its image in `.aleth_phases.json`. `docker_sandbox.run_isolated(..., image=…)` takes the resolved tag; an absent image the engine does not build is **pulled** (`pull_image`, bounded, logged) rather than refused, because requiring a manual pull before every new language is the friction that makes a monolith look attractive. The image is **`aleth-sandbox:latest`**, built from `docker/sandbox.Dockerfile` (Python 3.12 + pytest and the fundamental test utilities) and built once on first use when absent. An unreachable daemon or an image that cannot be provided raises `SandboxError` → a refusal, never a host run. `tools/sandbox.py` is deleted.

**The network boundary — Phase 12, severed by Phase 28, made two-phase by Phase 29.** Egress is off for everything the *model* can cause: the plan-declared `net` capability and its `--allow-network` flag were removed in Phase 28 (a prompt injection that can reach the network can exfiltrate `.env`), and `docker_sandbox.SANDBOX_NETWORK = "none"` is the default of `build_command`/`run_isolated`. Phase 29 added the one exception, and it is not reachable from a tool call: `SETUP_NETWORK = "bridge"` is used only by `tools/project_phases.run_setup`, which installs the project's dependencies from its own manifests *before* the LLM loop begins. There is no `docker network disconnect` because there is no long-lived container to disconnect -- this perimeter is one container per command (`--rm`), so the setup container's network namespace dies with it, which is stronger than detaching it. The model-facing surface (`tools/mcp_exec_server`) has no network parameter at all, asserted by signature and behaviourally against a live daemon in `tests/test_chaos.py`.

**Resource bounding — Phase 13.** Every container runs under a **bounded** hardware budget: `--memory`/`--memory-swap` at 512 MB, `--cpus` at 1.0 and `--pids-limit` at 64 by default. The bound is enforced by construction, not convention -- `docker_sandbox.build_command` clamps `memory_mb`/`cpus` to `MAX_MEMORY_MB` (8192) and `MAX_CPUS` (4.0) itself, so no caller can ask for an unbounded container. The only way to widen it is the `heavy` capability (4096 MB / 2.0 CPU), declared by the plan and threaded to the exec server's own argv (`--resource-profile`) exactly like `net` -- never a tool argument, so a model cannot buy itself memory. A container the kernel's OOM killer ends returns 137; `run_isolated` marks it `oom_killed` and `mcp_exec_server` writes `outcome = 'OOM_KILLED'` into `execution_telemetry` (the ledger gained an `outcome` column via a guarded `ALTER`), so the engine can tell a memory leak from a test failure instead of re-queuing the node. `tests/test_chaos.py::OomResilienceTests` proves it against a live daemon: a 64 MB container running a 1 GB allocation dies in seconds, the host survives, and the ledger records 137/`OOM_KILLED`.

**The orchestrator runs where the daemon runs.** The perimeter reaches the daemon through the `docker` client and treats the workspace path as a path *in the daemon's filesystem*; both are only true in one namespace, one filesystem and one signal space. So `docker_bin()` raises `EnvironmentError` when the client is not on `PATH` (surfaced as a `SandboxError` refusal at the tool boundary), and **nothing** translates paths or proxies commands across an OS boundary — no WSL bridge, no `wslpath`, no `\\wsl$` rewriting. Proxying `docker run` through another OS's interpreter would break the process-tree guarantee as well: killing the proxy leaves the container orphaned and unreachable by the timeout path. A workspace on a Windows drive (9p DrvFs) is **not** usable — a container writing through one creates files with no Windows ACL (mode 0000) — so when the daemon lives on Linux the orchestrator and its workspace live there too.

**Workspace location — the native cutover.** `tools/workspace.py` resolves `PROJECT_DIR` from `ALETH_WORKSPACE_DIR`, defaulting to `~/workspaces/my_project` (expanded, made absolute, and resolved against the repo root when relative). The workspace is a path *in the daemon's filesystem* — a container bind-mounts it — so it cannot be a directory beside the repository.

**Reads and writes are two different roots — Phase 20, made structural by Phase 23.** `PROJECT_DIR` is the user's live tree: the plan, the file explorer, the preview, source spans and the agent listing read it, and they must keep reading the real files while a run is in flight. Execution *writes* are a different question, answered by `tools/workspace.py::get_execution_dir()` — the staging root while a run is staged, `PROJECT_DIR` otherwise. Every write the agent can cause resolves through it: the MCP filesystem server's root, the container's bind mount, `executor.execute_approved`'s apply target, the planning context slice and `test_runner`'s working directory. `get_project_dir` is left to the read paths only. **Phase 23 makes the split structural rather than conventional:** the run's I/O and the frontend's reads are two modules with disjoint imports — `tools/execution_io.py` (the run's reads) imports `get_execution_dir` and cannot import `get_project_dir`, while `tools/workspace_io.py` (listing, preview, `.env`) imports `get_project_dir` and cannot reach the execution root. The run's root is also *injected* (`WorkflowContext.execution_root`, captured from the shadow at run start) rather than looked up by the tool, and a path outside the granted root is a hard `ValueError`.

**The shadow is the project as git sees it, keyed to one intent, and merges are serialised — Phase 21.** `tools/staging.py::create_staging` takes its file set from `git ls-files --cached --others --exclude-standard` (`_git_workspace_files`), so a virtualenv, a `node_modules` tree and a build output never enter a shadow; the ignore rules are pushed down to git rather than re-derived in Python, and a non-repository workspace falls back to a walk pruned by `IGNORE_DIRS`. The host side of a diff is filtered the same way, so an ignored file is never mistaken for one the agent deleted. `find_staging` resolves a shadow by its own id or by the intent that created it and **never** by plan — an execution id is the only key that maps 1:1 onto a shadow — and the diff/merge requests require it (`intent_id: str`). `merge_staging` runs under `merge_lock()`, a per-project `filelock` acquired non-blocking, so an overlapping merge raises `StagingLocked`, which `api/gateway.py` maps to a **409**. The UI remembers the intent id a run was submitted under (`state.activeIntentId`) and passes it back on `approve_artifact`, so an approved write joins that run's shadow instead of a new one nobody can reach.

**The plan pair is not a pair — Phase 11 state segregation.** `PLAN.md` stays in the user's repository: it is human-authored and git-tracked, and it belongs where it can be reviewed, diffed and reverted. The **machine state** does not: `aleth_state.db` lives in `~/.aleth/state/<project_id>/`, and `project_id` is resolved in tiers rather than from the filesystem path — an explicit `.aleth_id` beside the plan, else `sha256(canonicalised git remote + repo name)` (so an SSH clone and an HTTPS clone of one repository share an identity, and state survives a move or a container mount), else a minted UUID written to `.aleth_id` and added to `.gitignore`, and only as a last resort a hash of the absolute path — the one case reported as unstable. No binary file lands in the user's working tree. `plan.json` is legacy: read once for import, then removed, never written. `ALETH_STATE_DIR` overrides the state root (the suite points it at a throwaway directory).

**Immutable distribution — Phase 11.** `python -m build` produces `aleth-0.1.0-py3-none-any.whl` with the five packages and five top-level modules and **no** tests, bytecode or state files. `tools/verify_immutable_install.sh` proves the consequence rather than asserting it: it builds the wheel, installs it into an isolated venv, strips every write bit from the installed application, then boots the kernel and runs a plan — asserting the imports came from site-packages (not a nearby checkout), the store went to the state directory, and **no application file was added or changed**. A `chmod` is the only acceptable proof; an invariant assertion is not a substitute for the filesystem refusing a `write()`.

The native environment is `~/aleth-venv` (Python 3.12) plus `deepagents_core` built for Linux; the Windows venv still runs the suite where no daemon is needed.

**Declared dependency.** `pyproject.toml` declares `langchain-openai`: `create_deep_agent` constructs `ChatOpenAI` in every agent factory, so a clean environment cannot build an agent without it. It was previously satisfied only transitively, which a fresh Linux install exposed.

**Skill registry (`storage/db.py`, `orchestration/retriever.py`, `orchestration/system2.py`) — Phase 7.5.** A `skills` table (`id`, `name`, `target_capabilities` JSON, `markdown_content`), seeded idempotently with `TDD_Execution_Skill` for `["exec", "fs"]`. `retriever.skills_for_capabilities` matches a node's declaration with a **single** JSON1 set-intersection query (no N+1), and `system2.compose_system_prompt` prepends the block to the system prompt before the client payload is built. The planner resolves the block once per pass (`plan_task(capabilities=…)`) and passes it as text — the transport never looks a skill up.

**Engine verification gate (`orchestration/swarm.py`, `orchestration/workflow/execution.py`) — Phase 7.5.** `verification_refusal(verdict, required_capabilities)` is the policy: a node that required `exec` must carry a `tools/test_runner.py` receipt whose exit code is 0. No receipt, a failing receipt, or an uncollectable suite is a **refusal**, and the engine **intercepts the transition**: the node is re-queued (status `pending`, `rejection_attempts` incremented, so the retry is bounded by `max_retries` like a human's) with the message `Task unverified: Tests must be executed via test_runner and return exit_code 0`. It is never marked `completed` on the absence of evidence. A valid completion writes `tasks.verified = 1` in the same statement as the status (`update_task_status(..., verified=…)`).

**Swarm lifecycle (`orchestration/swarm.py`) — teardown hardening.** `drain(timeout)` waits for dispatched work to settle; `shutdown(timeout)` drains then closes; `BridgeAPI.shutdown_swarm()` is the app-side handle and the characterization harness drains it before unlinking a temporary workspace. A `Future` callback (`_on_worker_complete`) never raises — it reports to stderr, because nothing above a callback on the pool's thread can catch it.

**Swarm pool start method.** The pool does **not** inherit the platform default: `Swarm.tick()` builds its `ProcessPoolExecutor` with `mp_context=spawn`. `fork` (the POSIX default) copies the parent's native threads — lancedb's background loop, torch's pools — into the child as locks with no threads to release them, and a worker segfaulted on exactly that mid-suite. `forkserver` is thread-safe but its workers fork from a long-lived server whose environment is frozen when it starts, so a value set after the pool came up never reaches the child. `spawn` execs a fresh interpreter with the parent's *current* environment, which is the one that is both safe and correct.

**Planning-pass role binding — Phase 7 tail.** `planner.plan_task(role=…)` threads the node's role into `run_tool_loop`, and `worker.execute_node` passes its descriptor's role, so the planning pass asks the live `MCPSessionContext` for **that** role's tools instead of a constant. No import-time catalog exists anywhere; `tests/test_security_boundaries.py::NoImportTimeToolCatalogTests` pins the `@tool` catalogs and the native-shell shape at zero.

**Typed API boundary — Phase 14, unified in Phase 18.** `api/schemas.py` is the wire contract (strict `extra="forbid"`; `ServiceRefusal` encodes *a payload reporting an `error` must also report `success: false`*). `api/gateway.py` routes **bare infrastructure only** — `/api/health`, `/api/plans`, `/api/plan`, `/api/plan/{id}`, `/api/telemetry`, `/api/telemetry/{id}`, `/api/events`. Every engine capability is one row of `api/operations.py`, a closed table of typed operations; the intent surface included: `GET /api/intent/status`, `POST /api/intent/execute`, `POST /api/intent/acknowledge`. There is **no side-band intent route** — `tests/test_api_gateway.py::OperationTableTests` pins the frontend table and the server table 1:1 and the absence of a gateway intent route. The gateway caches every service answer against `ServiceRefusal` and answers 500 rather than forwarding a broken envelope; a `tools.staging.StagingLocked` from a merge is the one service exception it translates itself, into a **409**; `_drain_body()` runs before any refusal, so a refused POST answers a readable 403 instead of an RST.

**The queue and the service meet by injection.** `api/server.start_gateway` mints the queue and hands it to the service (`EngineService.attach_intent_queue`), so the intent operations are answered by the service without the test suite ever binding a socket. The queue mechanics have exactly one home, `api/intents.py` (`intent_status`, `submit_intent`), so the service and the test stubs exercise the same wire shape.

**The frontend is a browser on HTTP — Phase 15/16.** `ui/js/api-client.js` is the typed client, a 1:1 mirror of the operation table, and it **throws `ApiError`** on a transport failure *and* on an operation refusal (`try`/`catch` is the only way to observe a failure). `fatal.js` renders a blocking screen when the engine cannot be reached; `connection.js` tracks the SSE stream (`connecting/connected/reconnecting/lost`) and freezes the execution triggers after the 15 s grace. pywebview is a dumb browser: the page is served by the gateway at `/`, so the document origin *is* the API origin.

**Intent idempotency — Phase 17.** `storage/intents.py` writes `queued → running → completed | stopped | failed` **before** the run. A failure is terminal, never re-queued, and gates new work until `POST /api/intent/acknowledge` writes the acknowledgement in the ledger. `start_gateway` reconciles unfinished intents to `failed` at boot (the write-ahead pattern) and does not retry them.

**The autonomous loop — Phase 18.** `orchestration/autonomy.py` drives a plan when an `execute_plan` intent is dequeued. `plan_progress` reads the DAG in **one** aggregate query (no N+1); `next_move` decides from those counts alone — execute an approved (`in_progress`) node, plan a runnable one, or report a deadlock; `PlanDriver` runs the loop with the engine injected as three callables, so it is testable with fakes and a fake clock. **The human gate is never bypassed**: an artifact in `planned` is `AWAIT_REVIEW`, a terminal stop, not progress. `CircuitBreaker` enforces `MAX_TRANSITIONS = 25` and `PLAN_TTL_SECONDS = 900` *outside* the agent; a trip (or a step the engine reports it could not do) raises, the queue settles the intent `failed`, and the ledger gate holds the UI until a human acknowledges it. The frontend's un-targeted "Execute Next Step" submits `execute_plan`; a task card's own Execute — and any `[UI]` task, which needs its mockup — stays a single-node `next_step`.

**Knowledge graph — Phase 5.** `kernel://` URIs, entities/synapses with FK cascade, bidirectional depth-bounded recursive-CTE traversal, LanceDB vectors + outbox sync, hybrid retriever.

**Known accepted debt.**
(a) `agents/model_routing.py` remains the env seam the fleet is derived from; the UI settings panel still writes those variables.
(b) The sandbox image defaults to `aleth-sandbox:latest` and must carry whatever toolchain the workspace's commands need — the repo's `docker/sandbox.Dockerfile` supplies Python 3.12, pytest and the fundamental test utilities (`ALETH_SANDBOX_IMAGE` overrides it). A missing runner yields the `unavailable` verdict, never a host run.
(c) The orchestrator must run in the same namespace as the Docker daemon: the client must be on `PATH` (a missing client is a fatal `EnvironmentError`, surfaced as a refusal), and the workspace must live on the daemon's filesystem (`ALETH_WORKSPACE_DIR`). A workspace on a Windows drive is not usable (9p DrvFs writes land with no ACL). Nothing bridges the two by design.
(d) The Windows-side suite cannot exercise the daemon-backed tests (there is no docker client there), so they skip; the native WSL run is the one that proves containment.

*The Playbook and the Gatekeeper. Naked JSON schemas cause hallucinations; unverified text completions cause state corruption.*

   * **Mandate:** A node with code execution requirements (`exec` capability) **CANNOT** transition to `COMPLETED` based on LLM output alone.
   * **Rule:** Transitioning a task node to `COMPLETED` strictly requires:
     1. A valid tool receipt generated by `tools/test_runner.py` inside `tools/docker_sandbox.py` during that task's execution cycle.
     2. The tool receipt must explicitly confirm `exit_code == 0`.
     3. Setting `tasks.verified = 1` in the database upon state transition.
   * **Failure Handling:** If the LLM attempts to emit a completion signal without a valid `exit_code == 0` test receipt, the Swarm engine intercepts the transition, appends a rejection message ("Task unverified: Tests must be executed via test_runner and return exit_code 0"), increments `rejection_attempts`, and re-queues[cite: 4].

   * **Mandate:** During Swarm node dispatch, `orchestration/retriever.py` executes **one** SQL query to fetch active Skills where `target_capabilities` intersects with the node's `required_capabilities`[cite: 4].

     * `target_capabilities`: `["exec", "fs"]`

#### Phase 10: Chaos Engineering & IPC Brutality — sealed
*The Crucible. Proven: the system survives reality under load and unexpected process termination.*

* **Bounded streams.** `tools/stream_drain.py` keeps a head/tail window (1 MB) while draining both pipes as bytes arrive, so a child that floods stdio cannot block on a full pipe and the parent's memory stays bounded. `tests/test_chaos.py::PipeStufferTests` floods 20 MB through it.
* **Process groups.** Every child is spawned with `start_new_session=True`; a timeout kills the whole group (`os.killpg`) and reaps it. `ZombieEradicationTests` leaves zero survivors.
* **Environment.** `tools/env_sanitizer.py` builds the child's environment from an allow-list, so `.env` credentials never reach a payload; `test_environment_isolation` asserts `OPENAI_API_KEY` is undefined inside the execution context.
* **Descriptors.** `test_file_descriptor_leakage` proves 100 executions add no file descriptors.

#### Phase 11: Telemetry & Immutable Deployment — sealed
*The Finish Line. Complete visibility and zero environment drift.*

* **The forensic ledger.** `storage/telemetry.py` owns `execution_telemetry` (raw, indexed SQL): one append-only row per container execution -- `execution_id` (the container's own label), `session_id`, `target_tool`, `exit_code`, `duration_ms`, `outcome`, and a SHA-256 of each **full** stream, hashed as the bytes arrive (before truncation). Written by the exec server itself; a receipt that cannot be written is a critical fault, surfaced in the tool result and on stderr.
* **State segregation.** `PLAN.md` stays in the user's repository; `aleth_state.db` moves to `~/.aleth/state/<project_id>/`, with the identity resolved from `.aleth_id` → the canonicalised git remote → a minted UUID.
* **Immutability, proven.** `tools/verify_immutable_install.sh` builds the wheel, installs it into an isolated venv, strips every write bit, and boots the kernel as an unprivileged user -- the OS refusing a `write()` is the proof, not an assertion. Wired into CI as the `test-immutable` job.

#### Phase 13: Resource Bounding & OOM-Killer Protection — sealed
*The Cgroup. A container is isolated in software; without a hardware budget it can still take the host down.*

1. **Hard quotas.** Every `docker run` carries `--memory`/`--memory-swap` 512 MB, `--cpus` 1.0 and `--pids-limit` 64 by default. `build_command` clamps to `MAX_MEMORY_MB`/`MAX_CPUS` itself, so no caller can exceed the ceiling.
2. **Capability override, never unbounded.** The `heavy` capability (4096 MB / 2.0 CPU) is the only way to widen the budget; it is declared by the plan and threaded to the exec server's argv (`--resource-profile`), never a tool argument.
3. **OOM telemetry.** Exit 137 is marked `oom_killed` by `run_isolated` and recorded as `outcome = 'OOM_KILLED'` in the ledger, so a memory-leaking command is not retried as a transient fault.

## 4. The Sealed Ledger & The Active Objective

> **Phases 5 through 40 are sealed and verified in the native Linux and WSL environments. There is no open objective; the next phase awaits the Architect's directive.** V1 is complete and *operable*: the agent acts in an isolated sandbox, is steerable while it runs, can be rewound with its memory intact, its verified work leaves through one collision-gated extraction path, the ledger and the egress are hardened against the two ways a crash could corrupt state (Phase 39), and the operational layer -- keyring credentials, bounded structured logs, a refusing pre-flight -- makes it something an operator can run rather than a test stand (Phase 40).

**Phase 8 — Absolute Sandbox Isolation — sealed.** The exec server runs each command in a container (`tools/docker_sandbox.py`): the workspace is the only OCI bind mount and the container's working directory; `--network=none`; `--user <uid>:<gid>` maps the host identity so local file permissions are not mangled; CPU/memory/pids are capped; `--cap-drop=ALL` + `no-new-privileges`; and the process tree is owned by the named, `--rm` container, force-removed on timeout. The exec server's cwd is forced to the resolved workspace root, path traversal is refused before anything runs, and `execute_restricted_command` keeps the Architect's allow-list.
* **No native terminal fallback remains.** An unreachable daemon or a missing `docker` client is a **refusal** (`SandboxError`), never a host run. `tools/sandbox.py` is deleted.

**Phase 7 tail — dynamic tool binding in the swarm worker — closed.** The worker's planning pass asks the live `MCPSessionContext` for its **node's** role (`plan_task(role=…)` → `run_tool_loop`), and the agent factories bind from the same live `tools/list`. **Phase 11 — Telemetry & Immutable Deployment — sealed.** The append-only `execution_telemetry` ledger (raw SQL; SHA-256 of the full streams, taken on the fly), the plan-pair split (`PLAN.md` in the repository, machine state under `~/.aleth/state/<project_id>/`), and a read-only distribution proven by `tools/verify_immutable_install.sh` under a real `chmod -R a-w` in an unprivileged context. The `test-immutable` CI job is green.

**Phase 12 — Network Egress & Container Hardening — sealed.** `--network=none` is the default for every container. The plan-declared `net` capability that used to widen it was **removed in Phase 28**, which severs egress unconditionally.

**Phase 14 — API Gateway & State Segregation — sealed.** A loopback-only `ThreadingHTTPServer` serves the built frontend at `/` and a typed operation surface at `/api/*`; the frontend reads the plan and the telemetry ledger over HTTP and never touches SQLite; intents are *submitted* and the orchestrator drains them; the stream is SSE; the socket binds `127.0.0.1` and refuses a foreign `Host` and a cross-site `Origin`.

**Phase 15 — Frontend Cutover & Bridge Demolition — sealed.** Every `window.pywebview.api` call site is an `api-client.js` operation; the console is a gateway route (`/console.html`) so it shares the API origin; the bridge, its transport and its startup race are gone. The page is a browser pointed at the loopback socket.

**Phase 16 — Resilience & State Integrity — sealed.** A refusal and a transport failure both *throw* `ApiError`, so a call site that forgets cannot read fields off a payload that reports its own failure; an unreachable engine renders a blocking fatal screen instead of a white document; the SSE connection state is visible and freezes the execution triggers after the grace period.

**Phase 17 — State Reconciliation & Idempotency — sealed.** The durable `intent_ledger` is written before the run; boot reconciles every unfinished intent to `failed` without retrying it; an unacknowledged failure gates new work until it is acknowledged in the ledger. The gateway's response contract is single: an operation that reports an `error` without `success: false` is a 500, not a swallowed failure.

**Phase 18 — Unattended Autonomous Execution — sealed.** The intent surface is unified into `api/operations.py` (the side-band `GET /api/intents` and `POST /api/intent/execute` gateway routes are gone; `get_intent_status` / `submit_intent` are operations, and the frontend table maps 1:1). `orchestration/autonomy.py` drives a plan's DAG on an `execute_plan` intent: one aggregate query per transition, an approved node executed, a runnable node planned, a review stop at `planned`. `CircuitBreaker` (25 transitions / 900 s) is enforced outside the agent; a trip fails the intent and the ledger gate locks the UI. `tests/test_autonomy.py` proves the loop with fakes and a fake clock; the Playwright suite proves the frontend submits `execute_plan` for the plan-wide request and `next_step` for a targeted one.

**Phase 19 — Deterministic AI Routing & Handoff — sealed.** The agent decision is a typed gateway (`orchestration/routing.py`): `classify_task` is total — any classifier failure or malformed verdict routes to the Architect with `CLASSIFIER_FAULT` — and every decision is appended to the `routing_decisions` ledger. The classifier is injected, so the characterization suite is order-independent; the root cause of the reported "transient" flake was found, not excused: `env_boot` loads `.env` with `override=True`, arming `LAYA_BACKEND=model` mid-process. The one live-checkpoint test is `@pytest.mark.llm` and CI runs `-m "not llm"`. `tests/test_routing.py`, `tests/test_swarm.py::TestRoutingGateway` and `tests/test_laya_live.py` cover both halves.

**Phase 20 — Workspace Staging & The Merge Boundary — sealed.** Twenty phases of containment said nothing about the file system while the container was handed the user's uncommitted work as a read-write volume. `tools/staging.py` copies the workspace into a shadow under `<state_root>/staging/<staging_id>` (a manifest at its root is its durable identity), the run loop sets the execution root to that copy for the duration of the intent (`EngineService._staged_execution`, a nested call reusing the active shadow so the autonomous loop's passes accumulate), and `GET /api/workspace/diff` returns the content-addressed delta. `POST /api/workspace/merge` is the only path from the shadow to the host, and it refuses unless `autonomy.plan_progress(...).finished` — every task completed; a rejection purges the shadow and leaves the host untouched. `tests/test_staging.py` proves the copy, the delta, the merge, the purge, the gate and that `run_approved_artifact` and `test_runner` resolve the shadow rather than the host. This phase also surfaced and fixed a pre-existing suite-isolation defect: `env_boot` loads `.env` with `override=True` at `app` import, so a later test's assertion on a committed routing default was order-dependent; `tests/conftest.py` now clears the three `ALETH_*_MODEL` overrides around every test.

**Phase 21 — I/O Optimization & Concurrency Mutexes — sealed.** The shadow copy was an I/O bomb (it replicated `.git`, `node_modules`, a virtualenv and build output on every run) and its identity was ambiguous (a plan-keyed fallback let one run read another's delta). Both are gone. The copy is filtered by **git itself** — `git ls-files --cached --others --exclude-standard`, the only implementation that agrees with the user's own tooling; a hand-rolled matcher would have to re-derive negation, `**`, nested `.gitignore`, `.git/info/exclude` and the global excludes file, and an `rsync` subprocess would have to be handed those same rules anyway — with `IGNORE_DIRS` as the fallback for a non-repository workspace. `find_staging` accepts only a `staging_id` or an `intent_id`; the plan fallback is deleted, and a blank id is refused, so an orphaned shadow is dead by construction. `merge_lock()` holds a per-project `filelock` (`<state_dir>/merge.lock`) around the gate check *and* the apply, acquired non-blocking so a concurrent merge is a `StagingLocked` → **409**, not a queued wait. `_staged_execution` mints an id when none is given and reuses a run's existing shadow, so a manual approval joins the delta it is releasing. `tests/test_staging.py` adds the git-filter, orphaned-shadow, lock and same-intent-reuse cases; `tests/test_api_gateway.py::WorkspaceBoundaryTests` pins the 400 (missing id) and 409 (held lock); the Playwright suite proves the run's intent id reaches `approve_artifact`.

**Phase 22 — I/O Durability & State Bounding — sealed.** The engine severs runs on purpose — the 900 s plan TTL, the 512 MB cgroup ceiling — and a process writing a file at that instant dies with the run. `tools/atomic_io.py` is the answer: every durable write goes through a temporary file and one `os.replace`, so a reader sees the old bytes or the new bytes and never a mixture. The temporary is a **sibling of its target**, which is a requirement rather than a preference — `os.replace` is `rename(2)`, atomic only within one filesystem and `EXDEV` across two, and the shadow (`~/.aleth/state/<project>/staging`) and a merge's destination (the user's repository) are frequently two mounts; a `/tmp` temporary would be a third under WSL. The name carries the `.tmp` prefix the engine already treats as scratch (`staging._copy_ignore` prunes it from a shadow walk, `workspace_io.list_workspace_files` skips it in the listing), so a SIGKILL mid-write leaves litter no part of the system mistakes for a project file, and every failure path unlinks it. Refactored onto it: `mcp_fs_server.write_file` (the in-place truncation the directive named), `staging._apply_one` (the merge into the host — the highest-risk vector, where `shutil.copy2` wrote *into* the user's inode and a kill left half a file where their work was), `staging.create_staging`'s manifest, the three `plan_state` write sites (`PLAN.md` is git-tracked and human-authored), `ast_editor`'s splice, `workspace_io.overwrite_source`, and `recovery`'s snapshots, `_meta.json` and rollback restore. `tools/settings.py` and `orchestration/prompt_editor.py` are the two engine-source writers, converted on the same rule rather than left as exceptions. **State bounding** is `storage/retention.py`, wired into `main.py` immediately after the container sweep and before the bootloader: it fails every unfinished intent (`IntentLedger.reconcile` **first**, so a killed run's shadow is collectable on that boot rather than the next), trims the three append-only ledgers to their newest `LEDGER_KEEP_ROWS = 1000` rows with one `rowid`-keyed `DELETE` per table (each served by the recency index it already carries — no ORM, no migration framework), and calls `staging.purge_orphaned_stagings` with the ledger's own answer to which shadows are still owned. A shadow is kept while its intent is `queued`, `running` or `completed` — in use, or waiting to be reviewed — and collected otherwise, including a directory whose manifest a kill prevented from ever being written. `Storage.retention.sweep_state` never raises (`a boot that cannot tidy is still a boot`) and reports what it collected, zeros included, because a silent collector hides the crash that produced the garbage.

**Phase 23 — I/O Root Bifurcation & Context Strictness — sealed.** Phase 20 established that reads resolve the user's tree while execution writes resolve the shadow, but it left both behind one resolver in one module — and `overwrite_source`/`read_source` resolved against the *project* directory. The split is now structural rather than conventional: `tools/execution_io.py` owns the run's I/O (`overwrite_source`, `read_source`), imports `get_execution_dir`, and **cannot** import `get_project_dir`; `tools/workspace_io.py` owns the frontend's reads (listing, preview, `.env`), imports `get_project_dir`, and cannot reach the execution root. `tools/file_tools.py` re-exports both halves, so no import site moved. The root is **injected** rather than looked up: `WorkflowContext.execution_root` is captured from the shadow when the run starts (`runner.run_agent_workflow`) and threaded into `actions_impl._write_checked` and the three `read_source` call sites, and `tools.execution_io._resolve` raises a hard `PathDenied` (a `ValueError`) for any path outside the granted root — an injected root cannot be escaped with a filename. `read_source` was the **live** defect: `fix_bug` and `next_step` read the host while the patch was applied to the shadow over MCP, so a patch was computed against a stale base and a second step could not see the first step's edit. `overwrite_source` was **latent**: its only caller, `actions_impl._write_checked`, had no production caller — the executor writes through the MCP server, whose root is already the shadow — and Phase 24 deleted that function outright, so there was no longer anyone to wire it up wrong. Phase 25 then deleted `overwrite_source` itself, leaving this module a reader. `tests/test_staging.py::ExecutionRootBifurcationTests` formalizes the throwaway probe that found the breach: a read resolves the execution root and not the project, the UI reads still see the live project, an injected root is the only root, an out-of-root path is a `ValueError`, the module's *code* never names `get_project_dir` (pinned by AST, not by prose), and the orchestrator's context carries the shadow root.

**Phase 24 — Vestige Removal & Identity Atomicity — sealed.** Two loose ends Phase 23 surfaced, both closed by deletion or by one line. First, `orchestration/workflow/actions_impl._write_checked` was **dead code**: it had no production caller at all, and its docstring claimed the workflow published its deliverables through it. It did not — `executor.apply_artifact` writes through the **MCP filesystem server** (`client.write_file`), whose root is the shadow, so that is the established path and the function was a liability waiting to be wired up incorrectly. It is deleted, along with `WorkflowWriteGuardTests`, rather than kept "in case". Second, `tools/workspace.py::_mint_identity` wrote `.aleth_id` with a plain truncating write, which is the one non-atomic state write Phase 22 missed — and its failure mode was the worst in the system: `_identity_from_file` accepts anything matching `_SAFE_ID_RE`, so a *prefix* of the token (`a1b2c3` of a 32-hex id) is still a valid token. A kill mid-write would not fail validation, it would answer as a **different project** and orphan the entire state directory — plan DB, telemetry and staging — silently and permanently. It now goes through `tools.atomic_io.write_text_atomic`, so the file is the old id or the new one and never a prefix of one. `_ignore_identity_file`'s append is deliberately left alone: an incomplete line in a user's `.gitignore` is harmless and self-correcting, and does not warrant an atomic rewrite. `tests/test_state_identity.py::MintedIdentityTests::test_a_torn_mint_cannot_become_a_different_project` pins it by refusing the rename and asserting no partial token and no scratch file survive. One observation recorded, not acted on: with `_write_checked` gone, `tools/execution_io.overwrite_source` also has no production caller — it survives as the façade-pinned engine primitive with `FileOpTests` coverage and the Phase 23 shadow binding. Phase 25 acted on it.

**Phase 24 also closed a real Phase 10 race, found because CI went red on one Linux leg.** `test_chaos.py::ContainerLifecycleTests::test_mcp_server_sigterm_cleans_running_container` failed on `ubuntu-latest / py3.11` while `py3.12` and both Windows legs passed — the signature of a Linux-only, timing-sensitive test, since the container-backed tests only run where the daemon is. The defect was a **budget disagreement between two independent timeouts**: the exec server's SIGTERM handler removed its in-flight containers with `docker rm -f`, bounded by `KILL_TIMEOUT_SECONDS` (15 s), while the MCP client gave the process only `process_control.DEFAULT_GRACE_SECONDS` (5 s) before SIGKILLing its **whole process group** — and the handler's `docker rm` child was *in* that group. Under a parallel suite a removal slower than the grace was therefore killed mid-flight, and the container outlived the very server that was supposed to reap it. The fix is structural rather than a longer timeout: `remove_container(..., detached=True)` runs the removal in **its own session** with output to `DEVNULL` (no pipe whose reader is about to die), so the grace-expiry SIGKILL cannot reach it and the container dies either way; `purge_active_containers(detached=True)` is what the handler now asks for, while the timeout path and the sweeper keep the plain awaited removal. `tests/test_docker_sandbox.py::ContainerRemovalContractTests` pins the invocation (detached ⇒ `start_new_session` and no pipes; plain ⇒ captured and awaited), and the chaos test's observation window now matches the removal's own budget instead of a fixed 2 s — the assertion is unchanged. Verified on Linux with the daemon: the lifecycle class passed 8/8 (durations fell from a 5.17 s outlier, which was hitting the grace, to ~3.5–3.8 s) and the full Linux suite passed **1199 / 5 skipped**.

**Phase 25 — Dead-Code Purge & Project-Level Concurrency — sealed.** Three things, and the first is a deletion. **The purge:** `tools/execution_io.overwrite_source` is gone — from the module, from the `tools/file_tools` façade and its `__all__`, and from every test that used it as a subject. It had no production caller (`executor.apply_artifact` publishes through the MCP filesystem server, whose root is the shadow), so it was a second writer with a second set of rules and nothing left to use it; in a perimeter built to contain LLM filesystem access, an unused fully-armed writer is a liability, not a façade contract. The façade's `EXPECTED_EXPORTS` loses the name deliberately, and `test_star_import_yields_identical_tool_objects` now asserts its **absence**, so a re-introduction fails a test rather than a review. Tests that used it merely as a fixture write the bytes themselves (`WorkspaceTestCase.write`, which now creates parents; `test_staging._write` now writes verbatim so a fixture is platform-independent). **The mutex:** one intent may be `running` per project at a time, and the enforcement is the **ledger**, not the queue — the queue is in memory and dies with the process, while the ledger is shared by every engine on the project. `IntentLedger.claim` is a single conditional `UPDATE` (``status = 'queued'`` plus ``NOT EXISTS (… status = 'running' …)``) and it needs no project column and no second lock file, because the database is *already* per project: its path is ``<state_dir>/<project_id>/aleth_state.db``, so "no other intent in this ledger is running" *is* "no other intent of this project is running". Atomic in one transaction, so two engines draining one project cannot both see "nothing running"; `mark_running` is deleted (its only caller was the queue). `IntentQueue.take` claims **before** it pops, so an intent that cannot claim stays queued at the head, and `RunDeferred` — raised when the engine is busy with a run that did not come from the queue, machine-readable as `reason: "busy"` on the refusal — sends it back to `queued` via `queue.release` instead of failing it, because a concurrency condition is a reason to wait and not an outcome to record. `EngineService._run_intent` checks the run state *before* staging, so a deferred intent leaves no shadow behind. **The teardown:** the engine's own container sweep. `purge_managed_containers` force-removes every container carrying the ``aleth.managed`` label, **regardless of owner** — `purge_orphaned_containers` is the boot sweep and spares a live owner, which is exactly wrong at shutdown, where the owner is this process — and `install_shutdown_sweep` registers it on `atexit` **and** on SIGINT/SIGTERM, the handler restoring the default disposition and re-delivering the signal so the process still dies with the status its sender expects. It asks the daemon rather than trusting this process's bookkeeping, which is the point: a container is a child of `dockerd`, not of this process, so process-group scoping never reached it. The label is global rather than per project, so this sweep was **unscoped** here — and Phase 26 fixed that, scoping it to the engine's own process tree.

**Phase 26 — Teardown Precision & LLM Loop Bounding — sealed.** Three corrections, one of them a bug Phase 25 shipped. **The collateral damage:** `purge_managed_containers` matched the `aleth.managed` label alone, so an engine exiting killed the in-flight containers of *any* other engine on the host — a CI matrix leg, a background processor, another project. "One engine per machine" is an assumption a multi-tenant host does not honour. The sweep is now scoped to **this process's own tree** via `_is_our_child`, which walks the parent chain in `/proc` (`_stat_fields` was factored out of `_process_start_time` to read both field 22 and field 4 with one parser). Descendants rather than `os.getpid()` alone, and that distinction is the whole fix: the engine never creates a container itself — `run_isolated` runs inside the exec server *child*, so the containers it is responsible for carry that child's pid, and a sweep matching only its own pid would remove nothing. A container whose owner is already gone is still left alone: this engine cannot prove it made it, and the boot sweep is the one that can tell. `tests/test_chaos.py::ContainerLifecycleTests::test_the_shutdown_sweep_leaves_a_neighbours_container_alone` pins it on a live daemon with an `owner_pid=1` neighbour. **The loop ceiling:** `orchestration/workflow/agent_loop.py` had a `DEFAULT_MAX_TURNS = 6` that **silently returned an empty answer** when exhausted — a blank plan that looks like a decision. It is now `MAX_AGENT_STEPS = 30`, and hitting it records the fault in the ledger and raises `AgentStepLimitExceeded("Exceeded maximum execution steps")`. `planner._from_llm`'s broad `except Exception` (which means "the model did not return a plan") explicitly re-raises it, because a runaway loop is a different thing and swallowing it would turn the ceiling into a silent no-plan; the exception then propagates to the runner's `agent_error` + terminal `workflow_complete`, so the intent is **failed** with that message and the failure gate holds new work. **The tool-result budget:** `tools/result_budget.py` caps every string an MCP server hands the model at `MAX_RESULT_BYTES = 16 * 1024`, counting the marker — `truncate_result` middle-truncates (a head-only slice would cut away the traceback, which is where the diagnosis is) and states how much it dropped, so the model reaches for `grep` or a line reader instead of reasoning about a file it never saw. Applied to `mcp_fs_server.read_file` and to the exec server's `[Exit Code: N]` block (stdout + stderr). `tools.execution_io.read_source` is deliberately **not** routed through it: its caller writes the content back, so a truncation there would be silently written to disk. The fault ledger is a new append-only `agent_faults` table (its own table for the same reason `routing_decisions` has one: no container, no exit code, no route), bounded by the Phase 22 retention sweep and covered by `tests/test_mcp.py::ToolLoopTests` and `ToolResultBudgetTests`. Phase 27 then closed the gap this left: the row had no correlation id, so it was a detached record rather than evidence — see below.

**Phase 27 — Context Threading & Observability Lock-In — sealed.** Phase 26's fault row carried the fault and nothing that identified the run, which made it a detached record rather than evidence. **The correlation id:** `intent_id` is now threaded from the engine through every layer that could record or gate on it — `EngineService._launch_run` → `registry.run_agent_workflow` → `runner.run_agent_workflow` → `WorkflowContext.intent_id` → `plan_and_yield` → `plan_task` → `_from_llm` → `run_tool_loop` — and across the **process boundary** into swarm children, where it rides the role descriptor (`Swarm.tick(intent_id=…)` → `_descriptor_for` → `role_payload` → `worker.execute_node`), because a child cannot look it up. `agent_faults.intent_id` is `NOT NULL`, `record_agent_fault` **refuses a blank one**, and `agent_faults(db_path, intent_id=…)` is the join; the table's Phase-26 `session_id` — which nothing ever filled — is dropped by a guarded migration (the legacy index first, since SQLite refuses to drop a column an index still names), and the new index is created *after* the column migrations because it names a column an older table does not have yet. **The state bound:** the workflow layer gained a liveness gate. `IntentLedger.is_live` is one indexed read and `IntentLedger.abort` is a conditional `running → failed` write, so a parallel abort (a stop the user asked for, a breaker that tripped) is **durable** rather than a flag only its own thread can see — `EngineService.stop_execution` writes it. `run_tool_loop` takes an injected `ledger` (injected, not resolved, because the loop also runs in a swarm child whose plan directory is not the parent's) and checks liveness **before every step and before every tool call**, raising `RunAborted`: a tool that mutates is not allowed to overtake an abort that landed while the model was thinking, and `_record_step_limit` skips the telemetry write outright for a dead intent, because the engine must not write state or telemetry for a run that is already over. **The crash log:** `tools/run_context.py` holds the process's current intent (a module global, like `EXECUTION_ROOT`'s sibling, set by `_run_intent` and cleared in a `finally`) and `install_exception_logging` — called **first** in `main.py`, before the sweeps, so even a boot crash is correlated — installs both `sys.excepthook` and `threading.excepthook` to report `intent=<id>` on the same line as the failure while keeping the full traceback. `tests/test_run_context.py`, `tests/test_telemetry.py::AgentFaultSchemaTests` and `tests/test_mcp.py::RunLivenessGateTests` cover it.

**Phase 28 — Concurrency Safety, SQLite WAL & Network Airgaps — sealed.** Four fixes, one of them a bug Phase 27 shipped. **The correlation id is thread-safe:** `tools/run_context.py` held a module global, which in an engine with a thread per run and a `threading.excepthook` means thread B's id files thread A's crash -- logs worse than absent because they are confidently wrong. It is a `contextvars.ContextVar` now, isolated per thread and per asyncio task, and `tests/test_run_context.py` pins both halves: two concurrent threads hold different ids (deterministically, with a barrier), and a new thread does not inherit its parent's. Anything **not** on the run's thread asks the *queue* instead -- `stop_execution` runs on the API thread, where a context variable is invisible by design, so `IntentQueue.current` is the authority on what is in flight and the engine's abort uses it. **The supervisor records its children's deaths:** a worker that OOMs, segfaults or is SIGKILLed takes its interpreter with it, and a child that *does* raise reports into a `Future` the parent owns. `Swarm._handle_failure` now calls `_record_worker_fault` first thing, writing `kind=WORKER_TERMINATED` / `detail="Worker terminated unexpectedly"` joined to the tick's intent -- the run identity is captured into the callback at dispatch (`lambda … iid=intent_id`), because the callback fires on the pool's thread. The *reason* is not duplicated into the ledger: it is already on the node. **One configured connection:** `storage/connection.py` owns `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000` and `foreign_keys=ON`, and all eight call sites use it (the store, both ledgers, the retention sweep, the autonomy breaker, the retriever, the swarm and the worker). SQLite's default rollback journal locks the whole file for a write, so the UI polling while the orchestrator writes is `database is locked` -- a crashed engine rather than a slow one. **Egress is severed:** the plan-declared `net` capability and its `--allow-network` flag are **gone** -- `SANDBOX_NETWORK = "none"` is a constant, `build_command`/`run_isolated` have no parameter for it, and a plan that still declares `net` is told it has no effect. Two real bugs surfaced while verifying this: `_intent_ledger` was built from `get_store()` inside a swarm *child*, where the plan directory is not the parent's, so the gate read the wrong database (it now takes the `db_path` the child was handed); and `planner._from_llm`'s broad `except Exception` swallowed a `RunAborted` into `PlanningUnavailable`, reporting an engine fault as a model one (it re-raises now, like the step ceiling).

**Phase 29 — Two-Phase Execution, The Validation Gate & Absolute State — sealed.** Three things that turn the airgap from a cage into a workshop. **Two-phase execution:** an agent that cannot install its project's dependencies cannot test its own work, so `tools/project_phases.py::run_setup` runs the install **with egress** (`SETUP_NETWORK = "bridge"`) before the LLM loop starts -- deterministic, from the project's own manifests (a fixed table: `package.json` → `npm install`, `requirements.txt` → `pip install -r`, `pyproject.toml` → `pip install -e .`) or a human's `.aleth_phases.json`, never from anything the model wrote. A failed install **refuses the run**, because the loop only begins once setup has succeeded and a missing dependency should be reported as itself rather than as a model that wrote code nothing could run. There is no `docker network disconnect` to perform: this perimeter is one container per command (`--rm`), so the setup container's network namespace is destroyed with it -- stronger than detaching it, because no later command can inherit it. The sandbox image gained `nodejs`/`npm` here, which **Phase 30 reverted**: a runtime the project does not use is weight every project pays for, and the JavaScript sandbox is `node:20-alpine` selected per project instead. **The validation gate:** `run_verification` runs the project's suite **airgapped** over the finished shadow, and a failure fails the intent *and* writes `verified=false` into the shadow's manifest -- so `workspace_merge` refuses it and the review surface never offers a merge for work that does not run. `verified=None` meant "no suite was declared" here, which **Phase 30 sealed**: an unrun gate is a refusal now, and a project with no suite gets a structural syntax check instead. The verdict lives in the manifest rather than in the run's memory because the merge is a later request from the UI. **Absolute state:** `ALETH_STATE_ROOT` is the absolute path to the active project's state directory, and `storage/connection.py` owns both ends -- `state_dir()` derives and publishes **without overwriting** (so a spawned worker cannot clobber what it inherited by deriving from its own plan pointer, which is a *different* project), and `published_state_root()` is what a child reads, refusing a relative value outright. `publish_state_root()` -- the forced form -- is called only by the code that *moves* the pointer: `set_plan_dir`, `set_project_dir`, and a test fixture that repoints the directory. That is what retired the database-path baton through the swarm descriptor: `orchestration/worker.py` resolves the parent's database from the published root, and `planner._intent_ledger` does the same, so a child in another process opens the same file without being handed a path.

**Phase 30 — Dynamic Runtimes, Syntax Fallbacks & Supply-Chain Bounding — sealed.** Three corrections, two of them to Phase 29. **The monolith is dismantled:** node/npm are out of `docker/sandbox.Dockerfile` (verified inside the rebuilt container: Python present, `node` absent), and the runtime is selected per project from its own manifests — `package.json` → `node:20-alpine` (stock, pulled on first use by the new bounded `pull_image`), `requirements.txt`/`pyproject.toml`/`setup.py`/`pytest.ini`/`tox.ini` → the engine's own Python-toolchain image. A **polyglot** project is refused rather than guessed and declares its image in `.aleth_phases.json`. `run_isolated(..., image=…)` takes the resolved tag, so no single image carries every language. **The gate is sealed:** `verified=None` was a free pass and is now a refusal — a project with no suite gets the runtime's **structural syntax check** (`python -m compileall -q .`, or `npm run build` / a `node --check` sweep that skips `node_modules`), and a project whose runtime cannot be determined at all is marked failed rather than left unverified. The merge gate refuses anything that is not `verified is True`, so a shadow from an older build cannot slip through either. `tests/test_staging.py::MergeGateTests::test_an_unrun_gate_is_not_a_pass` and `…no_verdict_at_all_is_refused` pin the bypass shut, and `test_a_project_with_no_suite_is_still_mergeable` — which encoded the bypass — is gone. **The egress phase is bounded:** `DEFAULT_SETUP_TIMEOUT_SECONDS = 120` (clamped to a 600 s ceiling a human may raise in the declaration), because the setup phase is the only one with the network and a poisoned manifest or a circular dependency must not be able to hold the intent queue's only worker; a timeout kills the container, which takes its network namespace with it.

**Phase 31-32 — Rolling Context Compression & Hard Token Bounding — sealed.** The step ceiling bounded the *work*; these bound the *memory* and the *bill*, which are different limits. **The context is not linear.** Appending every prompt, diff and 16 KB tool result forever is how an agent bankrupts its user: by turn fifteen the payload is a hundred thousand tokens, the model's attention degrades into "lost in the middle", and every later call pays for the whole history again. `orchestration/workflow/agent_loop.py` now keeps `turns` (one entry per model turn) and sends a **three-block payload**: the immutable `system_prompt`, a rolling summary of everything older, and the last `CONTEXT_WINDOW_TURNS = 4` turns verbatim. Past `COMPRESS_AFTER_TURNS = 5`, `_compact` folds the rest into the summary with an injected `summarizer` — `planner._context_summarizer` runs the **cheapest configured slot** (`tier_0`), because summarising is bookkeeping and paying architect rates for it is the same waste the compression exists to prevent. No summarizer, a failing one, or an empty answer falls back to the FIFO drop plus an explicit system message (`TRUNCATION_NOTICE`, "Rely on the shadow workspace state"); the flag is **sticky**, so a model is told its history was truncated on every later turn rather than for one flickering step. The original user message is **pinned** and never compressed: it is the instruction the pass exists to satisfy. **The bill is bounded too.** `tools/token_budget.py` counts each call (tiktoken when an encoding loads **offline**, else the documented four-characters-per-token estimate — tiktoken's BPE files are downloaded on first use, and an offline engine cannot depend on that), `IntentLedger` accumulates `prompt_tokens`/`completion_tokens` with an `UPDATE ... + ?` so a swarm child's spend lands in the same row, and `TokenBudgetExceeded` is checked **before every LLM call and every tool execution** against `MAX_INTENT_TOKENS = 250000` (configurable). The planner re-raises it rather than letting the broad handler report a spent budget as "the model could not plan". **And the Node fallback no longer risks E2BIG:** `find . -type f \( -name '*.js' -o -name '*.mjs' -o -name '*.cjs' \) -not -path '*/node_modules/*' -not -path '*/dist/*' -not -path '*/.next/*' ... -exec node --check {} +` batches its arguments and prunes the build output, because expanding a compiled frontend into one argv is how the check fails on the very repository it protects.

**Phase 33 — Real-Time Observability & Hard Interruption (Live HITL) — sealed.** A run is no longer a black box the UI polls for a corpse. **The live stream.** `orchestration/workflow/agent_loop.py` emits structured events as they happen — `agent_thought`, `tool_execution_start`, `tool_execution_complete`, `token_budget_update` — through an injected `emit` callable that the engine threads from `EngineService.emit_event` (the bus) down through `run_agent_workflow` → `WorkflowContext.emit_fn` → `plan_and_yield` → `plan_task` → `_from_llm` → `run_tool_loop`; a swarm child has no bus to reach and leaves it `None`. Every event is a member of the strict bus union (`tools/payloads.py`) and is mirrored in `ui/js/bridge-bus.js`, so a frame the loop emits is the same frame a browser validates. **The per-intent stream.** `GET /api/intents/{intent_id}/stream` is a gateway *route* (not an operation: a stream has no single answer) that returns a `StreamResponse` carrying the id; `api/server.py` filters the hub's frames to that id, so a client following one run never sees a neighbour's. The unfiltered `/api/events` firehose is byte-for-byte unchanged. **The steering wheel.** `POST /api/intent/interrupt` holds a *running* intent (status `paused_awaiting_input`, distinct from `failed`: nothing went wrong, a person intervened) and `POST /api/intent/resume` releases it with the user's correction queued in the ledger — the only channel the API thread and the run thread share. The loop's gate observes the pause, announces `intent_paused`, waits up to `PAUSE_TIMEOUT_SECONDS = 900` for a payload, drains the corrections exactly once, injects each as a `[user]` message at the end of the high-fidelity window, and announces `intent_steered`/`intent_resumed`. **The gate drains on the running path too**, because a resume that lands before the loop's next gate observes the pause would otherwise strand the correction forever — a race the always-drain closes (`test_a_correction_that_lands_before_the_pause_is_seen_still_steers`). **The summary is capped.** The compressor is recursive (handed the previous summary plus the newly dropped turns) and its output is hard-truncated to `MAX_SUMMARY_TOKENS = 400` (head+tail), so a summariser that ignores its prompt cannot grow the payload on every fold. **The tokenizer is vendored.** The `cl100k_base` BPE blob (tiktoken's published SHA-256, checked by test) ships at `vendor/tiktoken/<sha1>`, `token_budget.install_cache_dir()` points `TIKTOKEN_CACHE_DIR` at it at boot, and the counter warns once on stderr if it must fall back — exact and offline, not a characters-per-token guess. `tests/test_mcp.py::SteeringAndStreamTests`/`ContextWindowTests`, `tests/test_characterization.py::SteeringBridgeTests`, `tests/test_api_gateway.py` (the route, the filter, the two operations) and `tests/test_token_budget.py::VendoredEncodingTests` pin each half.

**Phase 34 — Live HITL Dashboard & Stream Resiliency — sealed.** The backend primitives of Phase 33 had been piped into frontend handlers that dropped the frames on the floor; this closes the loop to the operator's screen. **The stream is rendered.** `ui/js/console.js` echoes `agent_thought`, `tool_execution_start`, `tool_execution_complete` and `intent_paused`/`_steered`/`_resumed` into the transcript, and `token_budget_update` drives a live burn counter in the console bar -- tokens spent against the event's own `limit` (the engine's `MAX_INTENT_TOKENS`, never a hard-coded number), amber past 80% and red at the ceiling. **The run is steerable from the screen.** An `Interrupt` control sits beside Stop in the top bar (`ui/js/live-run.js::interruptActiveRun` -> `POST /api/intent/interrupt`), and an `intent_paused` event reveals a steering overlay over the transcript whose two buttons release the hold through `POST /api/intent/resume` -- with the operator's correction, or without one. A refused resume keeps the overlay up and says why. **One connection, re-targetable.** `ui/js/stream.js` owns the single SSE connection and its path; `ui/js/live-run.js` points it at the run's own stream (`/api/intents/<id>/stream`) while a run is live and back at the firehose when it ends. Re-targeting rather than opening a second connection is what keeps a shared frame from being delivered twice. **The per-run stream carries the terminal event.** The server's filter (`api/server.py::_frame_for_intent`) was narrowed to "names this intent **or names none"**: an untagged event is a global one (the run's lifecycle, a plan change), and the engine runs one intent per project, so dropping it would leave a client following a run that had ended and never telling it. **Reconnect hydrates from the ledger.** `live-run.hydrateRunState` reconciles on every (re)connect from the durable ledger alone -- a held run shows the overlay, a terminal run is finalized (the missed `workflow_complete`), and a reloaded window adopts the run the ledger says is live. It deliberately does **not** consult `get_run_state`: the execution thread starts asynchronously, so reconciling against it would tear down a run the user had just launched (a race the first Playwright run caught). Hydration never replays the transcript, so nothing is duplicated. `tests/ui/live-run.spec.mjs` (9 tests) and `tests/test_api_gateway.py::IntentStreamFilterTests` pin each half.

**Phase 35 — Temporal Workspace Snapshots (Rollback) — sealed.** A shadow bounded the *blast radius*; it did not let anyone undo the damage. An agent that corrupts a module at step 12 and is interrupted at step 15 left a shadow that was simply wrong. Now the shadow carries its **own localized git repository** (`tools/snapshots.py`): `create_staging` initialises it and commits the workspace as handed to the agent as `step 0`, and after every `tool_execution_complete` the loop commits and tags the step -- **if git says a file changed**, which is a test no list of "tools that write" can make, because a shell command writes files too. The step number is monotonic for the *shadow*, not the pass (`snapshots.next_step`), because the autonomous loop drives several planner passes over one shadow and per-pass numbering would let pass two overwrite pass one. **The rewind is three things, and they must move together.** The files are restored by `POST /api/intent/rollback` (`git reset --hard` to the tag, then `git clean -fdx`), which is refused unless the intent is `paused_awaiting_input` -- the atomic ledger write *is* the gate, so the tree is never restored under a run that resumed meanwhile. The **context window** is restored by the loop from a per-step snapshot of `(turns, summary, steering)` taken when each step ended, and a rewind observed mid-step **drops that step's pending tool calls**: they were decided against context the operator has just discarded, and executing them would write files from the undone history. The **bill** is truncated by `IntentLedger.truncate_to_step`, which deletes the per-step rows after the target and recomputes the cumulative columns -- the cumulative is what the breaker reads, the rows are what makes "forget steps 13-15" expressible. `GET /api/intent/steps` lists the rewind points, and the steering overlay (Phase 34) grew a step picker and a Revert control. `tests/test_snapshots.py` (19 tests), `tests/test_mcp.py::SnapshotStepTests` and two Playwright tests pin each half.

**Phase 36 — Zombie Eradication & Hard Cleanup — sealed.** A daemon that dies without unwinding left containers and a ledger full of intents that were `running` with no process behind them. **The shutdown hook now does both.** `install_shutdown_sweep` takes an `extra` step, run first and independently guarded, and `main.py` passes `abort_running_intents`: on `atexit`, SIGINT and SIGTERM every `running` intent becomes **`aborted_by_system`** -- its own status, distinct from `failed`, because nothing the agent did went wrong, the machine did. It is terminal and it **gates** new work (`GATING_STATUSES` extends `pending_failure`/`acknowledge`), so the user is told their run was cut off before they can start another. The write is conditional on `running`, so the engine's own terminal write always wins and a repeated signal is harmless. **The boot reaper** is the existing container sweep -- a container is orphaned exactly when the process that created it is gone, which is a *stronger* signal than "not in the ledger" and the only one that is safe on a host running several engines. **Networks**: the engine creates none (every sandbox runs on Docker's built-in `none`, or `bridge` for the setup phase, so a container's namespace is created and destroyed with it), and `sweep_orphaned_networks` runs at every boot so that claim is a check rather than a promise -- `tests/test_chaos.py::ShutdownHookTests` searches the production modules for the call that would create one. One real bug fell out of the snapshot work: git writes loose object files **mode 0444**, which made a plain `rmtree` fail on Windows and leave shadows (and their read-only objects) behind forever -- every removal now goes through `staging.remove_tree`, which clears the bit and retries.

**Phase 37 — Global Context Serialization — sealed.** Phase 35's rewind restored the files and the bill but not the *memory*: the context window was an ephemeral Python array, so a rewind to a step that belonged to an earlier planner pass restored the body and left the brain behind -- and the next generation would hallucinate against a filesystem it did not remember. **The memory is now durable.** `intent_step_spend` gained a `context_blob` column (with a `STEP_MIGRATIONS` pass, because `CREATE TABLE IF NOT EXISTS` never adds a column to a table that already exists), and at the end of every step the loop serializes its exact memory -- the system prompt, the pinned task, the rolling summary, the verbatim window and the steering -- into that step's row. Structured rather than a flattened message array, and that is the stronger form: `_payload` reproduces the message array from those fields, so the blob *is* the array while staying readable and reconstructible. **Hydration is from the ledger, first.** `_rewind` reads the blob rather than any in-memory snapshot, so a rewind is exact even when the step belonged to an earlier loop invocation; the loop also drains a rewind the ledger still has queued **at boot**, which is the pass-boundary case, and `run_tool_loop(resume_context=…)` is the injection seam for a caller that already holds a blob. `tests/test_mcp.py::SnapshotStepTests::test_a_rewind_hydrates_memory_from_an_earlier_pass` is the proof: a second loop, with an empty array and a new step number, boots holding the first loop's step-1 memory and *not* step 2's. One consequence worth naming: truncating the bill now **zeroes** the later steps' spend instead of deleting their rows, because deleting them would make a second rewind -- to a step after the first -- restore the files with no memory to go with them.

**Phase 38 — Egress & Artifact Extraction — sealed.** The verified shadow was a hostage: there was no safe way to get finished code back to the host. `create_staging` now records a **baseline** -- the host as the run found it, `{path: sha256}` in `.aleth_baseline.json`, written before anything can change either side and committed into the shadow's step 0 so a rewind restores it too. Both halves of an egress are compared against that one point in time: the agent's delta is `shadow vs baseline`, and a **collision** is a path *both* sides moved -- any of the three kinds, because a person *deleting* a file the agent rewrote is as much a collision as editing it. `POST /api/intent/egress` is the extraction gate: it refuses unless the shadow is `verified is True`, refuses the whole egress on a collision rather than overwriting a person's work, and applies under the project's write lock with the collision check **re-run inside it** (a save can land between the review a person read and the click). The apply is all-or-nothing: the host files it will touch are copied aside first, so a failure half-way is rolled back rather than leaving a half-applied tree. `workspace_merge(approve=True)` now **delegates** to it, so the older name cannot be a second, ungated way onto the host; a rejection is unchanged. The UI offers **Apply to Project** in the top bar -- shown only when the engine's own diff read reports `mergeable`, because a UI that guessed the gate would offer an action the backend refuses. `tests/test_egress.py` (14 tests) and three Playwright tests pin it.

**Phase 39 — Hardening & Final Cut — sealed.** Two corrections, both of them mine. **Strict truncation.** Phase 37 zeroed the abandoned steps' spend instead of deleting their rows, reasoning that a later rewind would then still find their memory. That was wrong, and the reasoning was the tell: it tried to make a linear ledger behave like a branching one. A ledger is a log of the **active causal timeline**; an abandoned timeline's future steps do not exist. Zeroing left ghost rows, and the resumed run -- which numbers itself from the shadow's tags, not the ledger -- would either collide on `(intent_id, step)` or silently overwrite the forward memory. Now `truncate_to_step` **deletes** the rows and `snapshots.truncate_after` **drops the tags** in the same breath, and the loop resets `run_step` to `target + 1`, so the timeline reads `0,1,2` and the agent resumes at step 3 -- not at the number its abandoned future had reached. If a person wants step 5, they should not rewind to step 2. **Patch-safe egress.** The copy-aside rollback was a best-effort *in-process* recovery, and a SIGTERM or a power loss during it leaves the host half-written with nothing to fall back on. Now `apply_egress` writes an **uncapped, `git apply`-able patch** to `<host_root>/aleth_egress.patch` *before* the first host byte changes, and removes it only once the whole egress has landed: a clean run leaves no litter, and a crash leaves the agent's work one `git apply aleth_egress.patch` away. Two bugs fell out of writing it: a `limit=0` budget counted *down* from zero and truncated after one line, and a patch whose last line has no newline is a **corrupt** patch to git -- both caught by a test that runs `git apply --check`. **The audit** found no debug statements, no `breakpoint()`, no hardcoded absolute paths and no bare `except:` in the critical path; every broad handler in the loop is on an *observer* (telemetry, the compressor, the stream) and each says so, while the control path raises. It did find one thing of mine: an `OSError` writing the recovery patch escaped as a 500 rather than a refusal, which is fixed. `tests/test_egress.py` and `tests/test_snapshots.py` pin the rest.

**Phase 40 — The Production Harness — sealed.** An engine on a test stand is not a product. Three operational gaps, and the layer that closes them. **Zero-trust secrets.** A plaintext `.env` is a credential store in every backup, every screen share and one `git add -f` from a repository. `tools/secrets.py` puts them in the **OS keyring** (macOS Keychain, Windows Credential Locker, the Secret Service API) through `keyring` -- imported lazily, so a checkout without it still boots -- and `aleth keys set/clear/list` is the CLI surface. Two rules make it a boundary: the keyring is the *store* and the environment is the *hand-off* (`install_into_environment` loads what it holds into memory at boot; nothing opens a file for writing), and `list` reports **names only**, so a credential cannot leak into a terminal, a log or a transcript. An exported name wins over the store: the operator set it on purpose, and silently replacing it would be un-debuggable. **Structured, bounded logging.** `tools/engine_log.py` writes one JSON object per line -- timestamp, level, logger, message, and the run's correlation id when one is set (Phase 27) -- through a `RotatingFileHandler` capped at **50 MB × 3 backups**, under the *state* directory rather than the user's repository. `configure` is idempotent (the engine boots through several entry points, and a second handler would double every line). **The pre-flight enforcer.** `aleth boot` runs four checks -- container runtime reachable, `git` on the PATH, the API port free, and (informationally) a keyring backend -- and **aborts with a fix-it report** on any failure: every check carries its own fix line, because "it failed" is not a report, and the report shows the passes too so a user can see what was verified. No partial execution. `pyproject.toml` declares `keyring` and the `aleth` console script. `tests/test_harness.py` (27 tests) pins all of it, including the zero-trust claim asserted against the *bytes*: a credential loaded from the keyring leaves no occurrence of itself anywhere in the state directory or the ledger.
